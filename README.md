## 一、项目概述

### 1.1 项目简介

物品放行监控数据看板是一个**纯前端、完全离线**的 Excel 数据分析工具，面向厂区安保/物流管理人员，用于对「物品放行监控」系统导出的放行台账进行即时可视化分析。用户将导出的 `.xls / .xlsx / .csv` 文件拖入页面（或点击按钮选择），所有业务计算（字段映射、特保单识别、超时判定、结案率统计）**全部在浏览器本地完成**，数据不出内网、不依赖任何后端服务。

## 二、基础概念与术语解释

本章定义看板涉及的全部业务专有名词与统计口径，是理解分析逻辑、排查数据异常的**唯一基准**。所有口径均已在代码 `CONFIG` 与 `computeStats()` 中落地。

### 2.1 数据模型基础概念

#### 放行记录（行）与放行单（单）

这是理解全部指标的**前提**，二者不可混淆：

- **放行记录（Record / 行）**：导出文件中的**每一行**即一条放行记录，对应一件/一批物品的放行明细。一张放行单可包含多条记录（如一次放行多件物品）。
- **放行单（Order / 单）**：以 **`放行单号`** 为唯一标识的单据，由同一单号下的所有记录**聚合**而成。

> **示例**：某张单号 `WF7501260727000001` 的放行单包含 3 行记录（放行 3 件物品），则「放行记录总数」计 3，「放行单总数」计 1。

#### 放行单总数 vs 放行记录总数

| 指标 | 统计对象 | 计算方式 |
|------|----------|----------|
| **放行记录总数** | 文件数据行 | `rows.length`（总行数） |
| **放行单总数** | 去重后的单据 | 按 `放行单号` 分组后的组数（`computeOrders()` 的输出条目数） |

两者已合并展示在**同一个 KPI 卡片**（放行单总数）中：主数字为「放行单总数」，副标题显示「记录 N 条」。

#### 订单级聚合逻辑（按放行单号分组合并）

代码 `computeOrders()` 按 `放行单号` 对所有记录分组，为每张单生成一个订单对象。聚合规则采用「**任一命中即整单命中**」原则：

| 订单属性 | 聚合规则 |
|----------|----------|
| `已到达` | 该单**任一记录**已到达流入门岗 → 整单视为已到达 |
| `特保` | 该单**任一记录**为特保 → 整单视为特保单 |
| `放行超时` | 该单**任一记录**放行超时 → 整单视为放行超时 |
| `在途` | `!已到达`（尚未到达流入门岗） |
| `在途超时` | `在途 && 放行超时` |
| `记录数` | 该单包含的记录条数 |

> **业务含义**：一张单只要有一件物品出了问题（超时/特保），整张单即按问题单统计，符合安保"从严"管理原则。

### 2.2 核心业务术语

#### 特级安保单（特保单）

- **定义**：需要特级安保措施（专人押运、全程监控等）的高敏感放行单据。
- **识别规则（最新）**：**放行单号前六位为 `WF9897`** 即判定为特保单。
  ```js
  // CONFIG.特保单号前缀 = "WF9897"
  function isSpecialOrder(r) {
    return String(r.放行单号 || "").startsWith(CONFIG.特保单号前缀);
  }
  ```
- **⚠️ 重要变更**：旧版曾通过「物品类型含 *新产品A级物料 / 新产品机台* 关键词」或「单号含 `WF8888`」判定，**自 v2.2.0 起已全部废弃**，仅以单号前缀 `WF9897` 为唯一判定依据。
- **普通单**：单号前缀为 `WF7501`（`CONFIG.普通单号标识`），即非 `WF9897` 前缀的单据。

#### 已到达流入门岗

- **定义**：放行物品已实际抵达目的地门岗（流入门岗），流程接近完结。
- **判定逻辑**：`实际放行门岗 == 流入门岗`（两者均非空且去除首尾空格后字符串相等）。
  ```js
  o._已到达 = !!o.流入门岗 && !!o.实际放行门岗
           && String(o.实际放行门岗).trim() === String(o.流入门岗).trim();
  ```
- **业务含义**：`实际放行门岗` 记录该单最后一笔放行操作发生的门岗。若与目的地（流入门岗）一致，说明物品已送达；否则仍在运输途中。

#### 在途 / 在途超时 · 流入门岗未放行

- **在途**：放行单**尚未到达**流入门岗（`实际放行门岗 ≠ 流入门岗`，或实际放行门岗为空），物品仍在运输途中。
- **在途超时 · 流入门岗未放行**：在途**且**已放行超时的单据。即物品既未送达目的地，又已超过规定放行时限，属于**高风险滞留单**，是安保重点催办对象。
  ```js
  在途超时: !arrived && releaseTimeout   // 订单级
  ```
- **统计对象**：按**单**统计（订单级聚合后判定）。

#### 超时未接收

- **定义**：物品已在流入门岗放行（`实际放行门岗` 非空），但接收人**超过规定时间仍未完成接收确认**。
- **判定逻辑**（记录级）：
  ```js
  o._接收超时未接收 = !!o.实际放行门岗   // 已放行
                   && !o._接收日期        // 无接收时间
                   && o._接收超时;        // 且接收超时标记为真
  ```
- **业务含义**：放行已完成但交接断档，物品可能滞留在门岗无人认领，存在丢失风险。
- **统计对象**：按**记录**统计（满足条件的行）。

#### 放行结案完成率（核心 KPI）

- **定义**：在规定时间内到达流入门岗并**完成放行**的单据占「可判定单据」的比例，衡量放行流程的整体时效达成情况。
- **统计口径（v2.1.0 重新定义）**：
  ```
  分子（结案完成单）= 已到达 && 未放行超时 的单数
  分母（纳入统计单）= 结案完成单 + 到达但超时单 + 在途超时单
  放行结案完成率 = 分子 / 分母
  ```
- **关键规则**：**在途且未超时**的单据**不纳入统计**（分母中排除）。因为这些单据尚在正常运输途中，结果未知，强行计入会拉低/虚高完成率。
  ```js
  const closedOrders        = 已到达 && !放行超时;          // 分子
  const arrivedTimeout      = 已到达 && 放行超时;
  const transitTimeoutCount = 在途超时单数;
  const scopedOrders        = closedOrders + arrivedTimeout + transitTimeoutCount; // 分母
  const inTransitNotTimeout = !已到达 && !放行超时;         // 不纳入统计
  const closeRate = scopedOrders ? closedOrders / scopedOrders : 0;
  ```
- **数学自洽**：`纳入统计单 + 在途未超时单 = 放行单总数`。

#### 超时分类体系（广义超时）

「超时」是一个广义概念，完整分类如下（均为**订单级**判定）：

```
超时总数（广义超时 = 放行超时 ∪ 接收超时）
├── 放行超时（任一记录 _放行超时 → 整单超时）
│   ├── 在途超时：尚未到达流入门岗且已超时（流入门岗还未放行就已超时）
│   └── 到达超时：流入门岗放行时已超时
└── 接收超时（任一记录 _接收超时 → 整单接收超时）
    ├── 已接收但接收时超时：有接收时间 && 接收超时标记为真
    └── 超时未接收：无接收时间 && 接收超时标记为真
```

> 注：「在途超时」与「到达超时」互斥，两者之和 = 放行超时单数；「已接收但超时」与「超时未接收」互斥，两者之和 = 接收超时单数。标题明确标注「放行超时By××」的卡片仅统计放行超时；标题为泛称「超时」的指标（超时总数/NPI超时/特保物料超时/特保机台超时等）均使用广义超时口径。

> **NPI（新产品）即特保单**：特保单的物品分类仅有「A级物料」与「新产品机台」两类，因此 NPI超时 = 特保物料超时 + 特保机台超时（两个互斥子集）。

### 2.3 状态标识说明

| 状态字段 | 取值/判定 | 业务含义 |
|----------|-----------|----------|
| **放行超时** | 字段值 ∈ `{1, "1", "是", "Y", "YES", "TRUE"}`（`CONFIG.超时标记`） | 到达流入门岗时已超过规定放行时限 |
| **接收超时** | 同上 | 接收人未在规定时间内完成接收确认 |
| **放行异常** | `放行状态` 字段包含「异常」或「異常」 | 放行过程中出现异常（如物品不符、单据问题） |
| **已接收** | `接收时间` 非空 | 接收人已完成接收确认 |

> 超时判定使用 `isTimeout()` 函数，对字段值做 `trim().toUpperCase()` 后与 `CONFIG.超时标记` 逐一比对，兼容数字、中英文等多种导出格式。

### 2.4 全量卡片统计逻辑汇总（v5.1 共 21 张卡片）

> 本节记录 `dashboard-release-monitor-v5.1.html` 中全部卡片的统计口径、数据来源与计算层级，是审计口径一致性的唯一基准。

#### 2.4.1 统计层级说明

| 层级 | 含义 | 数据来源 |
|------|------|----------|
| **记录级** | 以 `rows[]` 中的每一行为统计对象 | `rows.filter(...)` |
| **订单级** | 以 `computeOrders()` 输出的订单对象为统计对象，任一记录命中即整单命中 | `orderList.filter(...)` |

> **全局口径原则**：一张放行单可含多条门岗放行记录，因此看板所有统计数字**一律以「单」（订单级）为计算单位**。仅以下场景保留记录级：① `kpi_overview` 副标题「记录 N 条」（明确标注）；② 明细数据表与下钻明细表（展示记录本身）；③ 实时流入动态栏（逐笔模拟流入）。

#### 2.4.2 KPI 指标卡（共 5 张）

| 卡片 ID | 名称 | 统计层级 | 数据源 | 精确计算公式 |
|---------|------|----------|--------|-------------|
| `kpi_overview` | 放行单总数 | 订单级 + 记录级 | `S.orderCount` / `S.total` | 主数字 = 按放行单号去重的订单数；副标题 = `rows.length` |
| `kpi_special` | 特级安保单 | 订单级 | `S.specialOrders` | `orderList.filter(o => o.特保).length` |
| `kpi_transit` | 在途超时未放行 | 订单级 | `S.transitTimeoutOrders.length` | `orderList.filter(o => o.在途超时).length`，其中 `在途超时 = !已到达 && 放行超时` |
| `kpi_receive` | 超时未接收 | 订单级 | `S.receiveTimeoutOrders.length` | `orderList.filter(o => o.超时未接收).length`，其中订单 `超时未接收 = 任一记录满足（实际放行门岗非空 && 无接收时间 && 接收超时）` |
| `kpi_rate` | 放行结案完成率 | 订单级 | `S.closeRate` | `closedOrders / scopedOrders`（公式见 2.2 结案完成率） |

#### 2.4.3 分布分析图表（共 6 张）

| 卡片 ID | 名称 | 统计层级 | 数据源 | 精确计算公式 |

**`gdms_timeout_trend` 每日聚合逻辑：**

```js

transitTimeout = arr.some(r => r._放行超时) && !arr.some(r => r._已到达)
closeRate = closed / (closed + arrivedTimeout + transitTimeout)
```

### v3.1.0 — Web Worker 后台解析 · 内联依赖 · CSV 转存

**发布日期**：2026-07-27 ｜ **类型**：功能优化版（MINOR）｜ **交付物**：`dashboard-release-monitor-v3.1.html`（不覆盖 v3/v2）

> 背景：v3.0.1 已将解析只剩 `XLSX.read` 一次主线程阻塞；本版将其移入 Web Worker 彻底消除主线程冻结。经实测：blob-URL Worker 在 `file://` 下可运行且能 `importScripts` 一个内存 blob，故可内联库实现单文件 Worker。

#### 🧵 Web Worker 后台解析（核心）

| # | 变更 | 实现方式 | 效果 |
|---|------|----------|------|
| 1 | **解析移出主线程** | 新增 blob-URL Worker（`PARSER_WORKER_SRC` + `parseViaWorker`），在 Worker 线程内 `importScripts` 内联库→`XLSX.read`→表头定位→分块提取，分块回传进度 | 主线程解析期间不冻结，彻底消除“页面无响应”弹窗 |
| 2 | **主线程兑底** | Worker 不支持/创建失败/报错时，自动回退到主线程分块解析（原 v3.0.1 路径） | 兼容旧浏览器/异常环境，不丢失可用性 |
| 3 | **表头异常不兑底** | Worker 回传 `NO_HEADER` 时直接报错（非基础设施故障，无需重试主线程） | 错误提示准确，不做无效重试 |

> 实测（5万行 xlsx）：Worker 路径下主线程最大卡顿仅 ~530ms（来自一次性图表渲染，非解析），而 v3.0.1 主线程解析仅 `XLSX.read` 就阻塞 ~1.8s。

#### 📦 内联 xlsx 库（单文件化）

| # | 变更 | 实现方式 | 效果 |
|---|------|----------|------|
| 4 | **xlsx 源码内联** | `<script src="./lib/xlsx">` 改为 `<script type="text/plain" id="xlsxLibSrc">` 内嵌整个库（已验证为合法 UTF-8、不含 `</script>` 与 `<script`，内联安全） | 去除 ./lib/xlsx 依赖，更接近单文件分发 |
| 5 | **主线程/Worker 共享副本** | 启动时由内联源码创建一个 Blob URL；主线程注入 `<script src=blob>` 加载（`xlsxReady`），Worker `importScripts(同一 blob URL)` | 单副本（仅 +约 861KB），两线程共用 |

> 已知代价：HTML 体积增加约 861KB（在“几MB以内”可接受范围）；其余依赖仍为 `./lib/` 引用，可后续按同模式逐步内联。

| # | 变更 | 实现方式 | 效果 |
|---|------|----------|------|
| 6 | **转存 CSV 按钮** | 新增“📄 转存 CSV”：将已加载数据按标准列分块生成 CSV（带 UTF-8 BOM），`FileSaver` 本地保存，全程离线无外网 | 将 xls 加载后一键转存为 csv，下次直接加载 csv，解析快约 20 倍 |

### v3.0.1 — 大文件解析进度与卡死修复

**发布日期**：2026-07-27 ｜ **类型**：Bug 修复版（PATCH）

> 背景：选取大容量源数据后，进度条长时间停在“正在解析文件结构”不动，随后浏览器弹“页面无响应”，数秒后直接跳到看板。

| # | 变更 | 根因 / 实现方式 | 效果 |
|---|------|-------------|------|
| 1 | **进度条只显示一个阶段** | 根因：`XLSX.read` 与 `sheet_to_json` 同步阻塞主线程，期间 UI 冻结无法刷新进度。新增 `sheetToRowsChunked`/`buildRowsChunked`，数据提取改为逐块读取 + 每块 `yieldUI()` 让出主线程 | 进度条完整展示 6 阶段（读取→解析工作表→定位表头→提取数据行 N/N→标准化 N/N→渲染） |
| 2 | **消除重复全表解析** | 原先 `findHeaderRow` 对全表调一次 `sheet_to_json(header:1)`、取数据又一次；现表头定位仅读前 20 行 | xlsx 解析开销减半 |
| 3 | **“页面无响应”弹窗大幅减少** | 去除重复解析 + 提取/标准化均分块让出主线程后，仅剩 `XLSX.read` 一步同步阻塞（file:// 离线环境下 Web Worker 不可用，已实测确认），且其前后有明确提示 | 大文件基本不再触发无响应弹窗 |

> 已知限制：`XLSX.read` 本身为单次同步调用，极大文件（十几万行）在极老机器上仍可能短暂阻塞数秒；已在其前显示“大文件可能需要几秒”提示。

### v3.0.0 — 性能自适应与老电脑友好重构

**发布日期**：2026-07-27 ｜ **类型**：新功能版（MAJOR）｜ **交付物**：`dashboard-release-monitor-v3.html`（不覆盖 v2）

> 背景：面向十年老电脑、小内存环境的专项性能优化。经源码审计定位，真正瓶颈是「永不停歇的动态背景 × 约 20 个实时重模糊的毛玻璃 × 全屏超高画布」这个视觉组合，而非数据计算。

#### 🔴 P0 核心：硬件感知的分级渲染

| # | 变更 | 实现方式 | 业务影响 |
|---|------|----------|----------|
| 1 | **硬件能力检测 PERF** | 新增 `PERF` 层：读 `navigator.deviceMemory`/`hardwareConcurrency`，内存≤4GB 或 核心≤2 自动判为低性能；手动选择存 `localStorage.perfMode` 优先 | 老电脑开箱即用最优档，无需手动配置 |
| 2 | **双档位渲染（full/lite）** | `body.perf-lite` 驱动 CSS 降级：去除全部 backdrop-filter、卡片改半透明纯色、关 hover 位移与动态栏动画 | 老机消除毛玻璃重模糊，滚动/交互丝滑 |
| 3 | **背景 Canvas fixed 化 + 视口尺寸** | 画布由 `absolute`+文档全高（可达 1920×4000）改为 `fixed`+仅视口（1920×1080），显存大降；移除 scroll 重建监听 | 消除滚动时已知卡顿源，降低填充率 |
| 4 | **低性能模式不启动 rAF** | lite 模式背景静态（CSS 渐变），不跑动画循环；高画质模式保留完整动态背景 | 老机静止时零背景开销 |
| 5 | **性能模式手动切换** | 顶栏⚙️按钮 + 状态标签，切换写入 localStorage 并 reload 确保 DPR/背景彻底重建 | 用户可自主选择画质/流畅侧重 |

## 四、版本管理体系

### 4.1 版本号规范（语义化版本 SemVer）

版本号格式：**`MAJOR.MINOR.PATCH`**（如 `2.2.0`）

| 段位 | 名称 | 递增时机 | 示例场景 |
|------|------|----------|----------|
| **MAJOR** | 主版本号 | **新功能版本**：新增独立功能模块、重大架构调整、全新业务逻辑、破坏性变更 | 接入新数据源格式、重构为组件化框架、新增"门禁联动"模块 |
| **MINOR** | 次版本号 | **功能优化版本**：现有功能改进、用户体验优化、性能提升、业务规则调整（向后兼容） | 动画丝滑化、KPI 合并、统计口径修正、大数据性能优化 |
| **PATCH** | 修订号 | **Bug 修复版本**：修复功能性缺陷、数据解析错误、显示异常、安全漏洞 | 修复表头误判、修复计数不刷新、修复内存泄漏 |

**递增规则**：
- 递增 MAJOR 时，MINOR 和 PATCH 归零（`2.2.3 → 3.0.0`）。
- 递增 MINOR 时，PATCH 归零（`2.2.3 → 2.3.0`）。
- 同一版本内多次修复可连续递增 PATCH（`2.2.0 → 2.2.1 → 2.2.2`）。

### 4.2 版本类型对照表

| 版本类型 | 号段特征 | 典型变更 | 历史实例 |
|----------|----------|----------|----------|
| Bug 修复版 | `x.y.Z` | 修复解析错误、显示缺陷、性能退化 | （预留：如 v2.2.1 修复某导出格式兼容问题） |
| 功能优化版 | `x.Y.0` | 体验优化、性能提升、规则微调 | v2.1.0、v2.2.0 |
| 新功能版 | `X.0.0` | 独立新模块、架构重构 | v2.0.0 |

### 4.3 发布流程

1. **开发**：在 `dashboard-release-monitor-v5.1.html` 上修改，遵循[第九章开发规范](#九开发规范)。
2. **自测**：
   - 载入演示数据，确认 KPI / 图表 / 实时模拟 / 二级详情全部正常；
   - 浏览器控制台**零错误、零警告**；

## 五、技术架构说明

### 5.1 架构总览

```
用户文件 (.xls/.xlsx/.csv)
        │
        ▼
  ┌─────────────┐   FileReader / XLSX.read / Papa.parse
  │  文件解析层   │   findHeaderRow() 智能表头定位
  └─────────────┘
        │  原始行数组
        ▼
  ┌─────────────┐   normalizeRow() 分块标准化
  │  数据标准化层 │   字段映射 / 日期解析 / 业务标记(_特保/_已到达/_超时)
  └─────────────┘
        │  rows[]
        ▼
  ┌─────────────┐   computeOrders() 订单级聚合
  │  业务计算层   │   computeStats() 汇总统计
  └─────────────┘
        │  orders{} + stats{}
        ▼
  ┌─────────────┐   ECharts / Tabulator / countUp / liquidFill
  │  可视化渲染层 │   液态玻璃动态背景 Canvas
  └─────────────┘
```

**架构特点**：单向数据流（解析 → 标准化 → 计算 → 渲染），全部逻辑在浏览器主线程完成，无后端、无构建步骤、无网络依赖。

### 7.4 性能模式（v3.0 新增）

v3 新增 `PERF` 自适应层，不属于 `CONFIG`，位于脚本顶部：

| 档位 | 含义 | 触发条件 |
|------|------|----------|
| **full（高画质）** | 完整液态玻璃：动态背景 + 毛玻璃 + 完整动画 | 内存 >4GB 且 CPU 核心 >2（自动） |
| **lite（流畅）** | 静态渐变背景 + 纯色卡片 + 关高开销动画 + 图表 DPR=1 | 内存 ≤4GB 或 核心 ≤2（自动） |

- **自动判定**：基于 `navigator.deviceMemory` 与 `navigator.hardwareConcurrency`。浏览器不支持 `deviceMemory`（如 Firefox/Safari）时按 8GB 保守估计。
- **手动切换**：顶栏⚙️「性能模式」按钮，选择写入 `localStorage.perfMode`（值为 `full`/`lite`），**优先于自动判定**；切换后自动 reload 生效。
- **状态标签**：顶栏显示当前模式（🖥️ 高画质/流畅），悬停可见检测到的内存/核心数与判定来源。
- **清除手动选择**：控制台执行 `localStorage.removeItem("perfMode")` 后刷新，恢复自动判定。

### 7.5 日常使用建议

- 每次从放行系统导出最新文件后直接拖入页面即可刷新全部分析。
- 分析结果可点击「导出分析结果 Excel」生成多 Sheet 报表，或「导出看板截图」保存 PNG 用于汇报。
- 页面可长时间挂起；大数据场景下建议关闭无关标签页以释放内存。

## 八、故障排查指南

### 8.1 常见问题速查

| 现象 | 可能原因 | 解决方法 |
|------|----------|----------|
| 提示「缺少必需列」 | 表头别名未覆盖 / 表头行未被识别 | 核对 6.3 别名表；若为新表头，在 `CONFIG.字段映射` 中追加别名 |
| 提示「未找到可识别的表头行」 | 文件无有效表头 / 表头在第 20 行之后 | 确认文件含「放行单号」等列；必要时手动删除多余标题行 |
| 提示「文件中没有读到数据行」 | 只有表头无数据 / 数据在第二个 Sheet | 确认数据行存在；当前仅读取第一个 Sheet |
| 解析失败乱码 | CSV 编码异常 | 系统已自动尝试 UTF-8→GBK；若仍乱码，用 Excel 另存为 UTF-8 CSV |
| KPI 计数显示 0 | 后台标签页 rAF 被浏览器节流 | 将标签页切到前台即自动恢复（非缺陷） |
| 大数据加载缓慢 | 文件行数过多 | 属正常现象，加载遮罩会分阶段显示实时进度（读取/解析/提取/标准化/渲染）；≥3万行已自动启用性能优化 |
| 进度条停在“解析工作表”不动 | `XLSX.read` 单次同步解析中 | v3.0.1 起仅此一步阻塞（无法分块），其余阶段均有进度；极大文件请耐心等待几秒 |
| 图表不显示/空白 | 容器尺寸为 0 / 窗口缩放 | 页面已内置 resize 自适应；刷新页面重试 |
| 截图导出模糊 | 默认 2x 缩放 | 已在 `html2canvas` 设置 `scale:2`；如需更清晰可调高 |
| 页面仍卡顿/掉帧 | 老机误判为高画质模式 | 点顶栏⚙️手动切为流畅模式（去毛玻璃/静态背景） |
| 性能模式不生效 | localStorage 被禁用 | 部分浏览器 file:// 下限制 localStorage；自动判定仍生效，手动选择不会记忆 |

### 8.2 错误处理机制

- **解析异常**：`handleFile` 的 `try/catch/finally` 统一捕获，toast 提示错误信息并**保证加载遮罩被关闭**（finally）。
- **字段缺失**：`processData` 检测必需字段，缺失时显示错误面板（列出缺失列 + 可用别名），不渲染看板。
- **日期容错**：`parseDate` 兼容 Date 对象、Excel 序列号、`YYYY/MM/DD`、`YYYY-MM-DD`、`YYYY年MM月DD日` 等多种格式，无法解析时返回 null 而非报错。

### 8.3 性能监控与调优

- **判断大数据模式是否生效**：控制台执行 `rows.length > CONFIG.大数据量阈值`，返回 `true` 即已启用。
- **查看当前性能档位**：控制台执行 `PERF`，可见 `{mem, cores, auto, mode, manual, lite}`；`lite:true` 即当前为流畅模式。
- **调优杠杆**：
  - 卡顿明显 → 首选手动切为流畅模式（⚙️）；或调小 `CONFIG.大数据量阈值` 使更多场景关动画；
  - 分块卡顿 → 调整 `CONFIG.分块大小`（减少让出次数或更平滑进度）；
  - 内存紧张 → 确认已释放原始数据（`processData` 中 `rawList = null`），且 Tabulator 已直接绑定 rows 不再复制。
- **浏览器任务管理器**：Chrome 菜单 → 更多工具 → 任务管理器，可观察本页面的内存/CPU 占用。

## 九、开发规范

### 9.1 代码组织原则

- **单文件架构**：所有逻辑保持在 `dashboard-release-monitor-v5.1.html` 内，便于离线分发与版本管理；不拆分外部 JS 文件。
- **配置与逻辑分离**：业务规则（字段映射、前缀、阈值）**只写在 `CONFIG`**；程序逻辑区一般不需修改。
- **单向数据流**：解析 → 标准化 → 计算 → 渲染，禁止逆向依赖（渲染层不得修改 rows/orders）。

### 9.2 命名约定

| 对象 | 约定 | 示例 |
|------|------|------|
| 配置项 | 中文名词 | `CONFIG.特保单号前缀` |
| 私有派生字段 | 下划线前缀 | `r._特保`、`r._已到达`、`r._申请日期` |
| 订单级属性 | 中文名词 | `o.在途超时`、`o.已到达` |
| DOM 获取 | `$()` 辅助函数 | `$("kpiOrders")` |
| 图表实例 | `liveCharts.*`（v4） | `liveCharts.chart_type`、`liveCharts.kpi_rate` |
| 计数器实例 | `counters.*` | `counters.kpi_overview` |

### 9.3 扩展接口说明

| 需求 | 扩展点 | 做法 |
|------|--------|------|
| 新增表头别名 | `CONFIG.字段映射` | 在对应字段的别名数组追加字符串 |

### 9.4 新增数据卡片指南（v5 自由布局）

**场景**：领导提出新指标需求时，无需新建页面，只需在 `CARD_DEFS` 注册一张新卡片，即可在卡片库中选用、拖拽、缩放、组合进任意视图。

**卡片定义规范**：

```js
CARD_DEFS.my_newCard = {
  id: "my_newCard",          // 唯一 id（布局中引用）
  title: "新指标名称",       // 卡片头显示标题
  icon: "📈",               // 卡片库/卡片头图标
  cat: "分布分析",           // 卡片库分组：KPI指标/分布分析/趋势分析/异常监控/明细数据
  w: 6, h: 3,               // 默认尺寸（宽×高，单位：网格列/行）
  minW: 3, maxW: 12,        // 缩放宽度约束（最小3列、最大12列）
  minH: 2, maxH: 6,         // 缩放高度约束（最小2行、最大6行）
  detailKey: "xxx",          // 可选：点击卡片打开的二级详情（KPI_DETAIL 的 key）
  render(body, ctx) {        // 必选：首次渲染。ctx={S:统计结果, rows, orders}
    body.innerHTML = '<div class="chart"></div>';
    cardChart("my_newCard", body.firstChild).setOption(optionBuilders.myOption(ctx.S), true);
  },
  update(body, ctx) {        // 可选：实时演示模式下的轻量刷新（缺省则重跑 render）
    if (liveCharts.my_newCard) liveCharts.my_newCard.setOption(optionBuilders.myOption(ctx.S));
  }
};
```

**尺寸参数说明**：

| 参数 | 含义 | 示例 |
|------|------|------|
| `w` | 默认宽度（占几列，总共 12 列） | KPI 小卡 `w:2`，图表卡 `w:6`，全宽卡 `w:12` |
| `h` | 默认高度（占几行，每行约 95px） | KPI `h:2`，图表 `h:3`，明细表 `h:5` |
| `minW/maxW` | 用户缩放时的宽度上下限 | 防止图表缩得太小无法辨认 |
| `minH/maxH` | 用户缩放时的高度上下限 | 防止 KPI 卡拉得过高浪费空间 |

**要点**：
- 图表类卡片用 `cardChart(id, el)` 初始化（自动纳入 `liveCharts` 生命周期，增删/缩放/resize 时正确销毁重建）。
- KPI 类卡片用 `countUp.CountUp` 创建计数器并存入 `counters.*`，`update` 中调 `.update(新值)`。
- 需要新统计口径时，在 `computeStats()` 中补充字段（自动被缓存），再在 `optionBuilders` 加 option 构造函数。
- 新增卡片**无需修改** renderDashboard/布局引擎/卡片库——它们都从 `CARD_DEFS` 动态读取。
- 若希望新卡片出现在某个预设视图中，在 `BUILTIN_LAYOUTS` 对应视图数组中加入 `{id:"my_newCard", x:0, y:0, w:6, h:3}`。
- 图表容器使用 `.chart` 类（`width:100%;height:100%`），确保缩放时图表自动填满卡片。

### 9.5 开发注意事项

- **离线优先**：任何新增依赖必须下载到 `./lib/` 并以相对路径引用，**严禁 CDN**。
- **向后兼容**：修改 `CONFIG` 字段时保留旧字段过渡；字段映射别名只增不删。
- **业务标记私有化**：`_` 前缀字段仅用于内部计算，`stripPrivate()` 会在导出/表格展示前剥离，勿在导出中暴露。
- **动画降级**：新增图表动画须经 `withAnim()` 注入，确保大数据模式下自动降级。
- **提交前自测**：演示数据全流程 + 真实文件（含合并标题）+ 大数据文件三类验证，控制台零错误。

### 10.2 统计口径类（问题 1 ~ 8）

> 以下问题均经逐行审计 `computeStats()` 与 `CARD_DEFS` 交叉比对确认，已全部修复（v5.1 迭代内修正，详见提交记录）。

#### ❗ 问题 1：「放行超时」在 chart_status 与 GDMS 卡片中统计层级不同（✅ 已修复）

**业务规则确认**：一张放行单经过多个门岗产生多条记录，该单是否超时由最后一笔记录的超时字段决定，超时是**订单级**属性。因此订单级是正确口径。

| 卡片 | 统计层级 | 状态 |
|------|----------|------|
| `gdms_timeout_dept` / `gdms_timeout_cat` / `gdms_timeout_duration` | 订单级 | ✅ 正确 |
| `chart_status`（statusDist.放行超时） | ~~记录级~~ → **订单级** | ✅ 已修正为 `orderList.filter(o => o.放行超时).length` |
| `overview` 详情「超时状态」维度 | ~~记录级~~ → **订单级** | ✅ 已修正为 `orders[r.放行单号].放行超时` |

#### ❗ 问题 2：「超时总数」(timeoutAll) 口径不完整（✅ 已修复）

**业务规则确认**：超时总数是广义概念 = 放行超时（含在途超时 + 到达超时）∪ 接收超时（含已接收但接收时超时 + 超时未接收），分类体系见 2.2「超时分类体系」。

| 指标 | 原口径 | 修正后 |
|------|--------|--------|
| `S.timeoutAll`（超时总数） | 放行超时 ∪ **仅超时未接收**，漏「已接收但超时」 | ✅ `orderList.filter(o => o.超时).length`（广义超时） |
| `S.timeoutNPI`（NPI超时） | 仅 `特保 && 放行超时` | ✅ `特保 && 广义超时` |
| `S.timeoutGeneral` | 仅 `放行超时 && 生产物料` | ✅ 死代码，已在问题 4 修复中移除 |
| `S.timeoutNPIMachine`（特保机台超时，原 timeoutMachine） | 仅 `放行超时 && 机台`，且缺特保过滤 | ✅ `特保 && 广义超时 && 机台`（见问题 4） |
| `gdms_timeout_dept/cat/duration` | 仅 `o.放行超时` | ✅ 保持不变（卡片标题即「放行超时By××」，口径与标题一致） |

配套改动：`computeOrders()` 新增订单级属性 `接收超时`（任一记录 `_接收超时`）与 `超时`（= 放行超时 ∪ 接收超时）。

#### ❗ 问题 3：gdms_timeout_trend 的「总超时」口径不完整（✅ 已修复）

- **原口径**：`_放行超时 || _接收超时未接收`，漏「已接收但接收时超时」
- **修正后**：`_放行超时 || _接收超时`（广义超时，与 timeoutAll 一致）
- 主看板 statusDist 的「接收超时」同步改为订单级广义接收超时，两处口径现已对齐。

#### ❗ 问题 4：gdms_summary 第 6/7 格重复展示相同数据（✅ 已修复）

原实现：

| 格位 | 标签 | 实际数据 |
|------|------|----------|
| 第 6 格 | NPI超时 | `S.timeoutNPI` |
| 第 7 格 | 特保物料超时 | `S.timeoutNPI` ← **相同** |

**业务规则确认**：NPI（新产品）指的就是特保单数据；特保单的物品分类仅有「A级物料」与「新产品机台」两类。因此特保超时细分应为特保单下的两个互斥子集，而非重复展示总数。

**修正后：**

| 格位 | 标签 | 修正后口径 |
|------|------|-----------|
| 6 | NPI超时 | `特保 && 广义超时`（保持不变，为下面两子集的父集） |
| 7 | 特保物料超时 | ~~`S.timeoutNPI`~~ → `timeoutNPIMaterial`：`特保 && 广义超时 && 物品分类含"A级物料/A級物料"` |
| 8 | ~~待保攜台超时~~ → **特保机台超时** | ~~`超时 && 机台`（缺特保过滤、标签错误）~~ → `timeoutNPIMachine`：`特保 && 广义超时 && 物品分类含"机台/機台"` |

**数学自洽**：特保物料超时 + 特保机台超时 = NPI超时（特保单物品分类仅两类）。

**配套清理**：移除 `timeoutGeneral` 死代码字段（无任何卡片引用）。

#### ❗ 问题 5：物品分类 split 处理不一致（✅ 已修复，split 逻辑已全部移除）

原实现中三种处理方式并存：

| 场景 | 处理方式 |
|------|----------|
| `materialClass`（三分类） | `split("/")` 后 `.some(c => c.includes(...))`，检查所有子项 |
| `timeoutByCat`（超时By物品类型） | `split("/")[0]`，**只取第一个** |
| `special` 详情图表 | 直接用 `r.物品分类`（不 split） |

**业务规则确认**：一张放行单建单后物品种类固定，中途不可能有其他物品掺入——**一单仅一种物品分类**；多记录仅因经过不同门岗产生。因此物品分类本不会出现 `/` 多值，split 拆分逻辑属于多余防御，且三种拆法并存导致跨卡片口径不一致。

**修正后**（全部直取分类值，不再 split）：

- `computeOrders()` 订单物品分类改为 `find(Boolean)`（取首个非空）替代 `join("/")`；
- `materialClass` / `timeoutNPIMaterial` / `timeoutNPIMachine` 改用直接 `includes` 判断；
- `catTop` / `deptCat` / `timeoutByCat` / `special` 详情图表直接按 `o.物品分类` 分组；移除 `firstCat` 辅助函数。

**配套修复**：原演示数据生成器与旧版 Python 脚本未遵守该规则（逐记录随机分类、特保前缀误用已废弃的 WF8888）。已重写 HTML 演示生成器 `makeDemoOrder`（一单 1~3 条门岗记录、分类整单固定、超时标记只打末笔、补入「已接收但超时」状态）；新增 `gen_monitor_data_v3.py` 生成合规测试文件 `物品放行监控_模拟测试.xlsx`（415 单/1202 行，已验证分类整单唯一、前缀 WF9897/WF7501、超时标记仅在末笔）。

> ⚠️ 旧脚本 `gen_monitor_data.py` / `gen_monitor_data02.py` 生成的文件特保前缀为已废弃的 `WF8888`，看板不会识别为特保单，仅供历史参考；测试请用 v3 生成的新文件。

#### ❗ 问题 6：statusDist「接收超时」实际是「超时未接收」子集（✅ 已修复）

- 原口径：字段名叫「接收超时」，但统计的是 `receiveTimeoutRows` = `_接收超时未接收`（需同时满足：实际放行门岗非空、无接收时间、接收超时标记为真）
- **修正后**：`orderList.filter(o => o.接收超时).length`，订单级广义接收超时（含「已接收但接收时超时」与「超时未接收」两个子集）
- 「超时未接收」子集仍由专属卡片 `kpi_receive` / `alert_receive` 展示，口径不变。

#### ❗ 问题 7：timeoutGeneral 可能重复计数（✅ 已修复）

原实现：

```js
timeoutGeneral = orderList.filter(o => !o.特保 && o.放行超时 && 含"生產物料").length
              + orderList.filter(o => !o.特保 && o.放行超时 && 含"生产物料").length
```

若某订单物品分类同时包含「生產物料」和「生产物料」（如 `"生產物料(非A類)/生产物料"`），会被**计数两次**。

**修正后**：先改为单一 filter 消除重复计数（见问题 2）；后续在问题 4 修复中，`timeoutGeneral` 字段作为死代码（无任何卡片引用）已被整体移除。

#### ❗ 问题 8：默认视图多个统计数字误用记录级口径（✅ 已修复）

**业务规则确认**：一张放行单可含多条门岗放行记录，看板所有统计数字一律以「单」（订单级）为计算单位。

本次统一修正的记录级统计：

| 位置 | 原口径（记录级） | 修正后（订单级） |
|------|------------------|------------------|
| `kpi_receive` / `alert_receive` | `receiveTimeoutRows.length` | `receiveTimeoutOrders.length`（新增订单属性 `超时未接收`） |
| `chart_trend` 申请量趋势 | 记录按日期计数 | 订单按申请日期计数 |
| `chart_dept` 部门 TOP10 | 记录 groupBy | 订单 groupBy |
| `chart_cat` 物品分类分布 | 记录 groupBy | 订单按 `o.物品分类` 直接 groupBy（问题 5 修复后不再拆分） |
| `chart_route` 门岗流转 | 记录 groupBy | 订单取最后一笔记录的流转方向 groupBy（新增订单属性 `流出门岗`） |
| `statusDist.放行异常` / `已接收` | 记录 filter | 订单属性 `放行异常` / `已接收`（任一记录命中即整单命中） |
| `chart_deptCat` 交叉分布 | 记录矩阵 | 订单矩阵（部门 × 物品分类） |
| overview 详情饼图/芯片 | 命中记录数 | 命中记录所属单去重数 |
| special 详情图表 | 特保记录按分类 | 特保单按物品分类 |
| receiveTimeout 详情 chips/图表 | 记录数/记录 groupBy | 单数/订单 groupBy |
| Excel 导出汇总/超时未接收 Sheet/部门排行 | 记录级 | 订单级 |

**保留记录级的场景**（均有明确标注或展示性质）：`kpi_overview` 副标题「记录 N 条」、明细数据表与各下钻明细表、实时流入动态栏、special 详情 chip「特保记录数」。
