技术评估与局限

1. 纯 HTML/CSS 能实现真实折射吗？

不能，至少当前规范下做不到。 CSS 的 backdrop-filter 规范支持的滤镜函数有限（blur、brightness、contrast、saturate 等），url() 引用 SVG feDisplacementMap 虽被部分浏览器实现，但存在：

  • 不对 backdrop 区域做几何位移，背景像素位置不变
  • 跨浏览器表现不一，Safari 行为与 Chrome 差异明显
  • 性能差，触发每帧重绘时帧率掉到 20 以下
结论：纯 CSS 只能"模拟"边缘效果（渐变描边 + 内阴影 + 切面高光），无法真正弯曲背景像素。

2. 拖动时折射会动态更新吗？

会，JS + Canvas 方案能实时更新。 实现思路：

  • 把"背景内容"（圆环、网格、渐变、装饰元素）画到一个全屏 <canvas id="bg-source">
  • 每个玻璃卡内嵌一个 <canvas>，根据 getBoundingClientRect() 把卡片所在区域的背景源复制进来
  • 对边缘 ~28px 环带做像素级位移和 RGB 通道分离采样（色散）
  • requestAnimationFrame 内重绘，拖动时同步更新
本 demo 第三张卡可拖动，背景折射会跟着位置和内容变化。

3. 需要哪些技术？内网能跑吗？

本方案是纯前端单文件 HTML，不依赖任何 CDN：

  • 必须：现代浏览器支持 Canvas 2D getImageData/putImageData（Chrome 76+ / Edge 79+ / Firefox 70+ / Safari 14+）
  • 不需：WebGL、Three.js、构建工具、Node 依赖
  • 不需：外网、CDN、npm 包
  • 整个 demo ~ 28KB，邮件分发即可
若要做"几十个玻璃卡同屏"，建议用 OffscreenCanvas + Web Worker，或降级到 CSS 近似方案。

4. 当前局限与优化路径

局限：

  • 边缘位移是基于背景"源 canvas"重绘，背景内容必须能被代码化绘制（DOM 元素不能直接采样）
  • 每帧 getImageData + 像素循环，单卡 300×200 约 6 万次运算，多卡同屏会吃 CPU
  • 不支持实时视频、跨域 iframe、外部图片作为背景

优化路径：

  • 把像素循环搬进 Web Worker，主线程只做合成
  • 改用 WebGL 着色器（片元 shader 算位移），单卡成本降到 <1ms
  • 用 OffscreenCanvas 离屏渲染，背景源持续更新而非每帧重绘
  • 若用框架（React/Vue），可封装成 <LiquidGlass> 组件，refractionStrength 暴露为 prop
