# 周报 / 月报自动化方案（规划稿）

## 1. 背景与约束

| 项 | 现状 |
|---|---|
| 数据量 | 每周导出约 **100 多 MB xlsx**，十几万单（约 40 列、一单多行） |
| 终端 | 部门电脑约 **4GB 内存**、十年前配置；Excel 打开原始文件极慢/卡死 |
| 固定任务 | 每周汇总（超时等关键指标）、每月汇总；成果是 **带图表的 Excel**，有时做 **PPT 汇报** |
| 可用资源 | 内网离线环境、本机 **Python 3.10**、公司 **Dify** 工作流平台、基于 Open Code 的编程智能体 |
| 已有资产 | 本项目看板（单文件 HTML，口径已成文）、三个数据生成器、CONTEXT 里的业务口径 |

### 已实测的硬约束

| 输入 | 压缩后 | 解压后 sheet XML | 浏览器能否解析 |
|---|---|---|---|
| 100,002 行 | 22 MB | 251 MB | ✅ 正常（27.8s） |
| 291,318 行 | 60 MB | 682 MB | ❌ `!ref` 为空 |
| 582,834 行 | 121 MB | 1,374 MB | ❌ `!ref` 为空 |
| 582,834 行 **CSV** | 212 MB | — | ✅ Papa.parse 5.0s（约 1GB 内存） |

**结论**：xlsx 进浏览器的上限 ≈ 21 万行 / 7 万单（≈512MB 解压 XML，V8 单字符串上限）；超过必然报「文件中没有可读取的工作表数据」。CSV 能解析，但 4GB 机器上 Chrome 峰值会到 2-3GB，**不可作为常规路径**。

## 2. 核心判断：不要把原始大文件塞进看板

业务上真正需要**人眼逐条看**的，只有「超时 / 未结案 / 异常」那一小撮（通常 <10%）。其余的价值在**汇总数字**。

因此架构上的分工是：

```
系统导出（100+MB xlsx）
      │
      ▼
[ETL 层]  Python 流式单遍扫描（标准库，零依赖，峰值内存 <400MB 预估）
      │
      ├──▶ 明细子集 CSV（≤5 万行）      → 拖进现有看板：秒开、下钻、单号直查
      ├──▶ 周/月汇总（几十行 CSV）      → 灌进 Excel 模板 → 图表自动刷新
      └──▶ summary.json（几 KB）        → Dify 写分析文字 / 邮件正文
```

**Excel 卡死的问题随之消失**：原始大文件全程不进 Excel，人只打开几十行的汇总表和几万行的明细子集。

## 3. 分层设计

### 3.1 ETL 层（新增，核心工作量）

**输入**：系统导出的 `.xlsx`（主）或 `.csv`（备）。
**实现约束**：

| 要求 | 做法 | 理由 |
|---|---|---|
| 零依赖 | 只用 `zipfile` + `xml.etree.ElementTree` 流式解析 | 内网不能 `pip install`；Python 3.10 开箱可用 |
| 内存可控 | 边解压边按 `</row>` 分块处理，**不把 sheet XML 整串读入** | 1.37GB XML 整读必 OOM；流式只持有一行 + 聚合字典 |
| 单遍扫描 | 一次读入同时产出明细子集 + 汇总 + summary | 大文件读第二遍代价高（预估单遍 2-5 分钟） |
| 口径可调 | 口径（特保判定、超时判定、部门归并、时长分档、结案率）**集中在一个配置段**，不散落在代码里 | 你要"先出原型再调"，改口径只改一处 |
| 幂等 | 输出按批次目录：`out/2026W48/`，重跑覆盖，不追加 | 避免人工清理 |

**复用现有口径**（CONTEXT.md 已成文，直接对齐）：
特保 = 单号前缀 `WF9897`；超时 = `放行超时`/`接收超时` 分钟数 `>0`（兼容旧 0/1 标记，状态列兜底）；「放行拒绝」不算异常、计入结案；部门取一级（去厂区后缀取第一段）；时长分档 `≤30min / 30min~1H / 1H~4H / >4H`；结案率公式同看板。

### 3.2 结果层（产物清单）

| 产物 | 体量 | 内容 |
|---|---|---|
| `明细_超时单.csv` | 1-5 万行 | 只保留超时/在途超时/超时未接收/未结案的单，40 列原样 → 看板可直接下钻 |
| `汇总_KPI.csv` | 1-2 行 | 总单数、结案率、放行超时、接收超时、超时未接收、在途超时 |
| `汇总_维度.csv` | 30-60 行 | 按一级部门 / 物品类型与分类 / 时长四档 / 门岗 TOP N 的超时单数与超时率 |
| `汇总_Top20.csv` | 20 行 | 超时最久的单（单号、部门、申请人、门岗、超时分钟） |
| `summary.json` | 几 KB | 上述汇总的结构化版 + 环比（与上期对比）字段，供 Dify / 邮件模板用 |

### 3.3 呈现层

**Excel（带图表）——推荐"脚本直出 + 样式集中配置"**

技术上有个坑要先说清：**openpyxl 读入再保存会丢失原有图表**，所以"拿你的模板填数据"这条路走不通（除非你不介意图表消失）。可行的是两条：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. xlsxwriter 直出**（推荐） | 代码里定义 sheet 结构 + 原生 Excel 图表（柱/折线/饼），样式参数集中在一个配置字典 | 每次一键出成品；图表是真 Excel 图表，可再编辑 | 首次要把版式写成代码（1-2 天） |
| B. 数据+模板分离 | 脚本只产 CSV，你粘进自己维护的模板 | 版式你完全掌控 | 每周手动操作一次，容易出错 |

`xlsxwriter` 是纯 Python 单文件库，**拷进内网即可用**，无需编译、无 numpy 依赖。

**PPT（汇报）**

- 阶段一：直接截 Excel 里生成的图表贴 PPT（零额外依赖）。
- 阶段二（可选）：`python-pptx` 填模板占位符 + 插入图片，脚本生成"每页一张图 + 一句结论"。同样纯 Python 可离线拷入。

### 3.4 Dify 的定位（明确边界）

**不做**：数据清洗、聚合、大文件搬运。原因是硬的——Code 节点是沙箱（内存/时长有限）、节点间靠变量传值（100MB 传不动）、无持久文件系统。

**做**（三选一或组合）：

1. **定时触发**：每周一 08:00 触发 ETL（调内网 HTTP 接口，或写触发文件给计划任务）。
2. **写分析文字**：读 `summary.json`，让 LLM 产出「本周超时集中在 X 部门，环比恶化 Y%，建议…」这类段落，填进周报/邮件。
3. **分发**：生成邮件正文、推送企微。

集成方式建议：Python 侧起一个极简 HTTP 服务（标准库 `http.server` 就够）暴露 `/run`，Dify 用 HTTP 节点调用；不通就用共享目录 + 计划任务，Dify 只读 JSON。

## 4. 内存与时间预算（4GB 机器的关键）

| 环节 | 预估 | 说明 |
|---|---|---|
| 流式解析 100+MB xlsx | 峰值 **300-400MB** | 内存按**单数**增长（聚合字典），不按行数；1.37GB XML 不会被整串载入 |
| 耗时 | **2-5 分钟** | 单线程 Python 流式；后台跑，不影响其它操作 |
| 产出报表 | 几秒 | 几十行数据写 xlsx |
| 看板载明细子集 | 秒级 | ≤5 万行 CSV，4GB 机器流畅 |

> 以上是**估算**，不是实测。阶段 0 的第一件事就是用现有 `物品放行监控_生成_200k.xlsx`（120MB / 58 万行）实测峰值 RSS 与耗时——**在你们的目标机器上测**，数字出来再决定是否需要换策略（例如把 ETL 放服务器）。

**兜底方案**（若实测内存吃紧）：分片跑——按申请日期把大文件切成 7 份（每天一份），逐份聚合后合并汇总。代价是多读一遍文件，但峰值内存可压到 100MB 以内。

## 5. 实施路线（分阶段，每阶段可独立验收）

| 阶段 | 内容 | 产出 | 验收标准 |
|---|---|---|---|
| **0. 可行性验证** | 流式解析 200k 文件，测峰值内存/耗时 | 一张实测数据表 | 目标机器上内存 <500MB、耗时 <10 分钟 |
| **1. 数据原型** | `etl.py` 出明细子集 + 4 个汇总 CSV | `out/2026W48/*.csv` | 汇总数字与看板同口径核对一致 |
| **2. 口径校准** | 用真实一周数据跑，你对比现有周报后提修改 | 口径配置定稿 | 你确认数字对得上 |
| **3. Excel 报表** | xlsxwriter 直出带图表的周报 | `周报_2026W48.xlsx` | 版式与现有周报一致或更好 |
| **4. 月报** | 整月聚合（按周累加，或按月分片跑）+ 环比 | `月报_2026-11.xlsx` | 与 4 周周报合计一致 |
| **5. 自动化** | 计划任务 / Dify 触发 + 文字生成 + 分发 | 双击 `.bat` 或定时 | 周一早上自动出周报 |

**建议顺序**：0 → 1 → 2 最关键，口径对不上后面都白做；3、4 是样式活；5 最后做。

| 风险 | 对策 |

## 8. 需求会变怎么办：固定引擎 + 可变配方（2026-11-27 补充）

### 8.1 先否掉一条路：每次都让模型生成一份新脚本

直觉上最省事——需求变了就让它写新脚本。但这在**周报这种"数字必须对得上"的场景**里会连环出事：

| 问题 | 后果 |
|---|---|
| 数字不可复现 | 同一份原始文件，两次生成的脚本算出来不一样，没人能解释差在哪 |
| 口径悄悄漂移 | 这次"放行拒绝"算进结案、下次不算，周环比直接失去意义 |
| 无法评审 | 代码是一次性的，没人会读 300 行新脚本；错了只能等报表发出去才发现 |
| 仓库污染 | 一年 52 份脚本，没人敢删、也没人看得懂哪份是现行的 |
| 复用率为零 | 第二次遇到八成相同的需求，还得从头生成——这正是"重复造轮子" |

### 8.2 把"会变的"和"不该变的"切开

| 会变（需求侧） | 不该变（执行侧） |
|---|---|
| 选哪几列、字段怎么映射 | 怎么流式读 100MB xlsx |
| 什么条件筛（超时>2h、某部门、某门岗） | 内存怎么控、分块怎么切 |
| 按什么分组、怎么聚合、怎么命名 | 数字自检、日志、产物落盘 |
| 排序取 TopN、时间窗口 | 编码坑、边界行、空值处理 |

**上层是配方（YAML/JSON，人能读能改），下层是引擎（代码，写一次）。** 需求变化只动配方。

### 8.3 配方的样子（示例，非最终语法）

```yaml
# recipes/周报_超时分析.yaml
source: 放行导出_2026W48.xlsx
filters:
  - {field: 放行超时, op: ">", value: 120}      # 只留超过 2 小时的
  - {field: 申请日期, op: between, value: [2026-11-20, 2026-11-27]}
derived:
  - {name: 一级部门, from: 申请部门, op: 一级部门归并}
  - {name: 超时时长档, from: 放行超时, op: 时长分档}
group_by: [一级部门, 超时时长档]
metrics:
  - {name: 超时单数, op: count_distinct, field: 放行单号}
  - {name: 超时率, op: ratio, of: 超时单数, base: 部门总单}
outputs:
  - {type: detail_subset, name: 明细_超时单.csv}
  - {name: 汇总_部门.csv, order_by: 超时单数, desc: true}
```

配方是人能审的：改一个 `value: 120` 就是"改成 2 小时"，不需要读代码。配方还能**版本化**——存进仓库，`git log` 就是口径变更史。

### 8.4 什么时候才该改引擎（判定规则）

- **变化只涉及"选哪些 / 什么条件 / 怎么分组 / 怎么排 / 怎么展示"** → 写配方，**不碰代码**。
- **出现新的计算语义**（新算法、新公式、新文件格式、新图表类型） → 让**编程智能体改引擎**，加一个算子，走 PR（D-35）。加了算子，以后同类需求又回到"写配方"。

这条规则能覆盖 90% 的日常变化。剩下的 10% 才需要动代码，而且是**扩充能力**，不是生成一次性脚本。

### 8.5 校验闸门（LLM 生成配置的最大风险就在这）

模型生成的配方不能直接跑，必须过三道闸：

1. **Schema 校验**：只允许白名单算子与字段名，模型编造的算子直接报错（不允许"自由发挥成脚本"）。
2. **守恒自检**：`放行超时 = 在途超时 + 到达超时`、`MP + NPI = ALL`、`时长四档之和 = 放行超时单数`、行数/单数与源文件可比。任何一条不成立就拒绝出报表。
3. **双跑对比**：新配方 vs 上一期配方在**同一份数据**上的结果差异，超过阈值（如 ±5%）要求人工确认后才能发布。

有这三道闸，模型出错是"跑不出来"，而不是"悄悄出一份错报表"。

### 8.6 看板也一样：生成"卡片定义"，不是生成 HTML

本项目看板 v5.6 已经是**插件化**的（`CARD_DEFS` / `BUILTIN_LAYOUTS` / 主题注册表 / 本地布局存储），所以"让模型生成一个新 HTML 模板"是错的抽象——那会回到多份 HTML 各自为政的老路。正确做法：

- 模型产出 **卡片定义 JSON**（用哪张卡、绑哪个字段、什么标题、放哪个视图、3×2 还是 4×1）；
- 现有看板渲染它，主题、深色、导出、单号直查全部继承；
- 新卡片类型（现有卡都不够用时）才让编程智能体加 `CARD_DEFS` 条目 + 渲染函数。

### 8.7 三方分工（避免重复造轮子）

| 角色 | 干什么 | 频率 | 产物 |
|---|---|---|---|
| **ETL 引擎 + 看板** | 执行配方、渲染卡片、自检 | 每次跑 | 数据与报表 |
| **Dify + 模型** | 自然语言 → 配方；`summary.json` → 分析文字；定时触发；分发 | 每周（或需求变时） | 配方文件、文字段落 |
| **编程智能体** | 给引擎加算子、给看板加卡片类型、修口径 bug | 偶尔 | 代码（走 PR） |

所以**不重复造轮子**：编程智能体不擅长"每周跑数、保证口径不漂"，Dify 不擅长"写和执行确定的计算"，你真正缺的是一层**配方 + 校验 + 复用库**——薄薄一层，不是另一个智能体。

### 8.8 演进路线

| 级别 | 形态 | 你要做的事 |
|---|---|---|
| L0 | 一份写死的 Python 脚本 | 需求变了改代码（现状痛点） |
| **L1** | 引擎 + 手写配方 | 需求变了改 YAML（**建议先到这**） |
| L2 | 配方库 + Dify 生成配方 | 自然语言提需求，模型出配方，人点确认 |
| L3 | Dify 全自动（定时触发 + 自动分发 + 文字分析） | 周一早上收周报 |

**建议至少先做到 L1 再谈 L2/L3**：L1 的配方语法稳定了，L2 让模型生成才有靶子；否则模型每次生成的东西结构都不一样，等于把 L0 的混乱搬进 AI 里，只是更快、更贵。

### 8.9 判断标准（以后遇到新需求，一句话自检）

> 这个变化，能不能用"已有的算子 + 换一组参数"表达？能 → 配方；不能 → 加算子。

## 10. L1 已落地：引擎 + 第一份配方（2026-11-27）

### 10.1 文件

| 文件 | 作用 | 会不会变 |
|---|---|---|
| `etl_engine.py` | ETL 引擎：流式读 xlsx/CSV、订单级聚合、按配方出报表 | **写一次，基本不动** |
| `recipes/weekly_overtime.json` | 周报超时分析配方：阈值、时长分档、看哪些维度、每维取前几名、明细子集规则 | **需求变了改这里** |
| `out/<批次>/` | 产物（本地，不入库） | 每次重生成 |

### 10.2 跑法

```bash
# 常规：系统导出 xlsx 直接跑（口径要反复调时，只在第一次慢）
py etl_engine.py --input 放行导出_2026W48.xlsx --recipe recipes/weekly_overtime.json --batch 2026W48

# 加速：先转一次 CSV，之后重跑快约 9-15 倍（同级 CSV 会复用）
py etl_engine.py --input 放行导出_2026W48.xlsx --recipe ... --batch 2026W48 --cache-csv
```

### 10.4 性能实测（同一份 20 万单 / 58.26 万行数据）

| 输入形态 | 读取耗时 | 总耗时 | 峰值内存 |
|---|---|---|---|
| **xlsx**（121MB，解压 XML 1.37GB） | **224-231s** | 235s | 274-397MB |
| **CSV**（212MB） | **14-15s** | 24s | 397-400MB |

- 换算读取吞吐：xlsx ≈ **2.5k 行/秒**；CSV ≈ **3.9 万行/秒**（差约 15 倍）。
- **不要用 openpyxl / pandas 读大 xlsx**：openpyxl 约 188 行/秒，58 万行要 51 分钟。本引擎走 `zipfile` + `iterparse` 流式，比它快约 13 倍，但**仍是 CSV 的 1/15**。
- 峰值内存 ≈ 400MB（主要来自 20 万单的订单级聚合字典 + 明细 spool），4GB 机器可跑；老机器按 2-3 倍时间预留（约 10-15 分钟）。
- 首选加速永远是**让系统直接导 CSV**；导不出来就用 `--cache-csv` 转一次。
- 可选进阶（需离线拷 wheel，非必需）：`python-calamine`（Rust 内核，读 xlsx 快 10-50 倍）或 `polars`。内网装包要下 `cp310/win_amd64` 的 whl 拷进去；不装也能跑，引擎不依赖它。

### 10.5 改需求怎么做（不碰代码）

| 需求变化 | 改哪里 |
|---|---|
| 超时阈值 1 小时改 2 小时 | `--min-minutes 120` 或配方 `detail_subset.min_minutes` |
| 时长分档改成 1h/4h/24h | 配方 `duration_buckets_min` |
| 多看一个维度（如按申请人） | 配方 `dimensions` 加一条 `{key, label, top}` |
| 某个维度少看几行 | 配方里该条 `top` 调小 |
| 明细子集规则换（只看放行超时） | 配方 `detail_subset.rule` |

只有当出现**新的计算语义**（新公式、新算法、新文件格式）时，才改 `etl_engine.py`。

### 10.6 已知限制

- 只读第一个工作表；多 sheet 的导出需先拆。
- 时间列只认 `2026/11/27 08:30:00` 一类格式（`%Y/%m/%d`、`%Y-%m-%d` 混排的分钟格式也兼容）。
- 订单级聚合假设「同单号的行」能靠字典归并（不要求连续），但**超大文件（>100 万行）内存会到 1GB 以上**，届时按天分片跑。
- 输出目录在 OneDrive 下时，偶发 `OSError 22`（同步锁），已改为先写 `.tmp` 再替换并重试 5 次。
